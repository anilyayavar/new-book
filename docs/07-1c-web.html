13  Data from Web Pages

Last updated

23 October 2026

Much of the information an auditor needs is published on the internet, and only there. A state e-procurement portal lists every tender, with the date it was published and the date it closed. It also shows who won each contract, and at what value. A department publishes the list of firms it has debarred. A price portal shows the rates notified for cement or medicines. None of this comes to us as a file. It is spread over web pages, ten or twenty rows to a page.

Yet these pages answer real audit questions. Was a tender really published for the required number of days, or only for a week? Is the contract value in the division’s register the same as the value the portal shows? Has the division paid a firm that the State had already debarred? To answer them, we must compare the auditee’s records with what was published. Copying a few hundred rows from a website by hand is slow, and it brings typing errors. R can read the pages for us. This is called web scraping.

In this chapter we learn to do it with the package rvest.

  • What a web page is made of, and how to look at its structure with the browser’s Inspect tool.
  • Reading a page, and picking out its parts with CSS selectors.
  • Taking text, links and tables out of a page, and cleaning them into dates and amounts.
  • Reading many pages one after another, and following links to detail pages.
  • Two audit use cases, on the time tenders were kept open and on payments to debarred firms.
  • Keeping a dated copy of the pages as audit evidence, and scraping a real website responsibly.

The book does not depend on any live website. Websites change, they may block programs, and copying a real portal’s pages raises questions of permission. So we use a small mock website made for this book, saved as plain HTML files in the folder Data/web. It imitates the e-procurement portal of an imaginary “Example State”. Every name on it is made up. The methods are exactly those we would use on a real site.

Prerequisites

13.2 What a web page is

A web page is a text file written in HTML (HyperText Markup Language). The browser reads the file and draws the page. The text is marked up with tags in angle brackets. Most tags come in pairs, an opening tag like <p> and a closing tag like </p>, with the content in between. Together they make an element.

Here are the tags we meet most often.

Tag What it holds
<h1>, <h2> Headings
<p> A paragraph of text
<a href="..."> A link. The address it points to is in href
<ul>, <li> A list, and an item of the list
<table>, <tr>, <th>, <td> A table, a row, a header cell and a data cell
<div>, <span> Containers used to group things, for layout

An opening tag may carry attributes, written as name="value". Two attributes matter most for scraping. The class attribute puts an element in a named group, such as class="amount", usually so that the page can style all amounts alike. The id attribute gives an element a name that is unique on the page, such as id="tender-list". Elements sit inside other elements, like boxes inside boxes. A <td> is inside a <tr>, which is inside a <table>.

Let us make a tiny page with minimal_html(), which turns a piece of HTML in a string into a page R can read.

tiny <- minimal_html('
  <h2>Notice board</h2>
  <p class="notice">Pre-bid meeting on <b>12-Nov-2024</b> at 11:00</p>
  <p class="notice">Last date extended to <b>29-Nov-2024</b></p>
  <a class="doc" href="nit-2024-131.pdf">Download NIT</a>
  <table>
    <tr><th>Item</th><th>Rate</th></tr>
    <tr><td>Cement (bag)</td><td>420</td></tr>
    <tr><td>Steel (quintal)</td><td>6,150</td></tr>
  </table>')

13.3 Looking inside a page with Inspect

To select elements, we must know how the page is built. Every modern browser can show this. Open tenders-page1.html in Chrome, Edge or Firefox, right-click on a tender amount and choose Inspect. A panel opens beside the page, showing the HTML, with the element we clicked highlighted.

<tr><td>1</td><td class="tender-id">2024_PWD_131</td>
    <td class="title">Construction of CC road, Ward 7, Amarpur</td>
    ...
    <td class="amount">&#8377; 48,60,000.00</td>
    <td class="status">Open</td></tr>

Move the mouse over the lines in the panel. The browser shades the part of the page each line draws. In a few minutes we can learn the plan of the page. Here, each tender is a row <tr> of the table with id="tender-list". Each cell has a class that names its content, such as tender-id, published, closing or amount. The “Next” link has class="next". (&#8377; is the code for the rupee sign ₹.)

We then write CSS selectors, short patterns that pick elements. They are the same patterns web designers use to style pages. These few cover most needs.

Selector Picks
td Every element with the tag td
.amount Every element with class="amount"
#tender-list The element with id="tender-list"
td.amount Every td with class="amount"
#tender-list tbody tr Every tr inside a tbody inside the element #tender-list (a space means “somewhere inside”)
a[href] Every link that has an href attribute
a.next The link with class="next"

In the Inspect panel, right-click an element and choose Copy, then Copy selector, to get a selector the browser writes for us. It is often long and fragile, like body > main > table > tbody > tr:nth-child(3) > td:nth-child(7). A short selector built on a meaningful id or class, like td.amount, is better, because it still works when a row is added or the layout changes a little.

TipAudit tip

Before writing any code, spend five minutes with Inspect on two or three pages of the site. Note the id of the table, the classes of the cells, how the “Next” link is marked, and whether detail pages have the same plan. Write these down in the working papers, with the date. If the site changes later, this note explains why the old code no longer works.

13.5 Cleaning scraped text

Everything taken from a web page is text. Dates come as “18-Nov-2024 10:00” and amounts as “₹ 48,60,000.00”. Before any analysis we turn them into proper types. Let us write one function that reads a tender page into a clean table. We will reuse it for every page.

read_tender_page <- function(file) {
  rows <- read_html(file) |> html_elements("#tender-list tbody tr")
  tibble(
    tender_id   = rows |> html_element("td.tender-id") |> html_text2(),
    title       = rows |> html_element("td.title") |> html_text2(),
    org         = rows |> html_element("td.org") |> html_text2(),
    published   = rows |> html_element("td.published") |> html_text2(),
    closing     = rows |> html_element("td.closing") |> html_text2(),
    value       = rows |> html_element("td.amount") |> html_text2(),
    status      = rows |> html_element("td.status") |> html_text2(),
    award_link  = rows |> html_element("a.award-link") |> html_attr("href"),
    source_file = basename(file)
  ) |>
    mutate(published = dmy_hm(published, tz = "Asia/Kolkata"),
           closing   = dmy_hm(closing, tz = "Asia/Kolkata"),
           value     = parse_number(value))
}

Two functions did the cleaning.

  • dmy_hm() from lubridate (Chapter 18) reads a date written day first, with the month as a word, followed by hours and minutes. We give the time zone "Asia/Kolkata", since the portal shows Indian time.
  • parse_number() from readr (Section 10.5) drops the rupee sign and the commas and keeps the number. It does not care where the commas are, so Indian grouping like “1,24,50,000” is read correctly as 12450000.

We also kept source_file, so that every row can be traced back to the page it came from.

WarningCaution

parse_number() reads the first number it finds in the text. A cell like “₹ 12.5 lakh” becomes 12.5, not 12,50,000. A cell like “Rs. 5,00,000” gives NA with a warning, because the full stop after “Rs” confuses it. Remove such prefixes first, for example with str_remove(x, "Rs\\.?"). Look at a sample of the raw text before trusting the conversion, and check how many values came out as NA. Dates need the same care. A page may show “02/12/2024” on one screen and “2-Dec-24” on another.

13.6 Many pages, one after another

A portal rarely shows everything on one page. Ours shows six tenders to a page, with a “Next” link. There are two ways to read all the pages.

When the addresses follow a pattern. Our pages are tenders-page1.html to tenders-page3.html. On real portals the pattern is often in the address itself, like .../tenders?page=2. We build the addresses with paste0(), read each with map() (Section 7.5), and stack the results with list_rbind().

13.8 Audit use case, were tenders open long enough?

A tender must stay open long enough for every interested firm to see it and prepare a bid. A short window favours a firm that knew about the work in advance, and reduces competition. In our example, suppose the procurement rules of Example State require at least 21 days from publication on the portal to the closing date. (This is an example norm for our imaginary state. 13.9.1 Cleaning the names before matching

The names on the portal and in the payment register are written differently. One has “SHIVAM CONSTRUCTIONS PRIVATE LIMITED”, the other “Shivam Constructions Pvt. Ltd.”. An exact join would find no match at all. So we first bring both to a common form, as in Chapter 20. We change to capitals, remove “M/s” and “(P)”, write “&” as “AND”, drop punctuation, and drop words like “Private”, “Limited” and “Co” that say nothing about who the firm is.

clean_firm <- function(x) {
  x |>
    str_to_upper() |>
    str_remove("^M/S\\.?\\s*") |>
    str_remove_all("\\(P\\)") |>
    str_replace_all("&", " AND ") |>
    str_replace_all("[[:punct:]]", " ") |>
    str_squish() |>
    str_remove_all("\\b(PRIVATE|PVT|LIMITED|LTD|AND CO|CO)\\b") |>
    str_squish()
}

WarningCaution

Scraped data is only as good as the page it came from, and web pages change. A tender may be corrected, a firm removed from the debarred list, or the whole portal redesigned. If the auditee later disputes a finding, “the website showed it” is not evidence unless we can show what it showed and when. So, for every scrape, record the address of each page and the date and time of collection, and save a copy of each page exactly as received, in the working papers.

13.11 Scraping a real website responsibly

Everything above works on a real website by giving read_html() a web address instead of a file. But a real website belongs to someone, and runs on a server that others need too. A scraper sends requests much faster than a person clicking. Careless scraping can slow a site down for everyone, break its terms of use, or be blocked as an attack. An auditor must be beyond reproach here. Follow these rules.

  1. Look for an official source first. Many portals offer a download in Excel or CSV, an open data page, or an API (a service that gives data to programs). Ask the department or the portal’s owner for the data. Scrape only if there is no better way.
  2. Read the site’s terms of use and its robots.txt. The file robots.txt, at the root of a site, says which parts programs may not visit, and sometimes how long to wait between requests. Respect both.
  3. Identify yourself. Send a “user agent” that names your office and gives a contact address, so the site’s owner knows who is visiting and why.
  4. Go slowly. Wait a few seconds between requests, and never send requests in parallel. Scrape outside office hours, when fewer people need the site.
  5. Never log in or break any barrier. Do not use anyone’s password, do not try to get round a CAPTCHA, a login page or a block, and do not visit pages that are not open to the public. If the data is behind a login, ask for it officially.
  6. Take only what you need, once. Save the pages (Section 13.10) and work on the copies, rather than reading the site again and again.

The code below shows how a polite scraper of a real portal may look. It is not run in this book, and the address https://eprocure.example.gov.in is a placeholder, not a real portal. It uses httr2, which gives more control than read_html() alone. req_user_agent() identifies us, req_throttle() limits the rate of requests, req_retry() tries again a few times if the server is busy, and req_perform(path = ...) saves each page to a file. The pause with Sys.sleep() keeps us well within the 10 seconds the site asked for.

library(httr2)

base_url <- "https://eprocure.example.gov.in"   # placeholder, not a real portal

# 1. Read the site's rules first
request(base_url) |>
  req_url_path("robots.txt") |>
  req_perform() |>
  resp_body_string() |>
  cat()

# 2. A polite request, that names us and goes slowly
polite_request <- function(url) {
  request(url) |>
    req_user_agent("Audit team, Office of the Accountant General, Example State (audit.team@example.gov.in)") |>
    req_throttle(rate = 5 / 60) |>        # at most 5 requests a minute
    req_retry(max_tries = 3) |>
    req_timeout(60)
}

# 3. Save each page, as received, in a dated folder
evidence_dir <- file.path("evidence", paste0("eprocure-", format(Sys.Date(), "%Y-%m-%d")))
dir.create(evidence_dir, recursive = TRUE, showWarnings = FALSE)

urls  <- paste0(base_url, "/tenders?page=", 1:3)
files <- file.path(evidence_dir, paste0("tenders-page", 1:3, ".html"))
for (i in seq_along(urls)) {
  polite_request(urls[i]) |> req_perform(path = files[i])
  Sys.sleep(15)                           # a pause between pages
}

# 4. Analyse the saved copies, exactly as in this chapter
tenders <- files |> map(read_tender_page) |> list_rbind()

Some websites build their pages with JavaScript after they load. read_html() then gets only an empty frame, without the table we see in the browser. Open Inspect, go to the Network tab and reload the page. Often the data arrives from an API as JSON, which httr2 can read with resp_body_json(), after checking that the site allows it. rvest also has read_html_live(), which runs a real browser in the background. 13.12 A suggested workflow

  1. Look for a better source. An official download, an API, or a request to the department.
  2. Read the rules of the site. Its terms of use and robots.txt. Note them in the working papers.
  3. Study the page with Inspect. Find the id of the table, the classes of the cells and the “Next” link, and choose short, meaningful CSS selectors.
  4. Save the pages first. Politely, with a user agent and pauses, into a dated folder, with an evidence log of addresses, times and checksums.
  5. Read the saved copies. Write one function for one page, using html_elements() for rows and html_element() for the cells in each row, then map() it over all the pages.
  6. Clean the text. Dates with dmy_hm() or dmy(), amounts with parse_number(), and names with a cleaning function.
  7. Check completeness. Compare the rows read with the total the site shows, and look for repeats and NAs.
  8. Compare with the auditee’s records. Join on IDs and cleaned names, test dates against the norm, and confirm every hit from the documents before reporting it.
ImportantRemember
  • A web page is HTML. Tags make elements, and the class and id attributes help us select them with CSS selectors.
  • read_html() reads a page, html_elements() and html_element() select, and html_text2(), html_attr() and html_table() extract.
  • Select the rows first, then one cell from each row with html_element(), so that the columns line up.
  • Read many pages with map(), or by following the “Next” link, and check that the count matches the site.
  • Scraped data is evidence only if we record where and when it was collected, and keep a copy.
  • On real sites, prefer an official source, respect the rules, identify yourself, go slowly, and never log in or get round a barrier.
