52  Network Analysis in Audit

Many frauds are about connections that someone wants to hide. In a welfare scheme, one person registers several times, each time with a slightly different identity, and draws the benefit several times. In a Public Works Division, a few firms bid against each other in every tender, but they are really one group. In GST returns, the same goods “move” round a circle of firms on paper, to create a false turnover. In an office, a vendor is secretly linked to the employee who passes its bills. Each of these leaves a trace in the data. The trace is hard to see in a table, but easy to see in a network.

In Chapter 51, we learnt the ideas of graph theory and the tools to work with networks in R. In this chapter we apply them to four audit problems.

  • One person behind many registrations in a scheme, found with connected components.
  • A cartel of firms which always bid together, found with communities.
  • Invoices going round in a circle between a few firms, found with cycles.
  • A vendor linked with an employee, found with components and shortest paths.

The recipe is nearly always the same. We turn the records into a graph. We reduce the graph to the parts that matter. We find the structure we are looking for, like a connected group, a cycle, a community or a path. Then we go back to the records. At the end of the chapter, we collect tips for working with the large networks that real audit data produces.

52.1 Prerequisites

We will use tidyverse for data handling, igraph for the analysis, and visNetwork to draw interactive networks. In each interactive network of this chapter, you can zoom, drag the vertices, hover over them for details, and click a vertex to highlight its neighbours.

library(tidyverse)
library(igraph)
library(visNetwork)

52.2 Audit use case 1, one person behind many registrations

Imagine a scheme where each person has several IDs, such as a mobile number, an email ID, and an ID issued by a Government Department, like the PAN in India. Using the techniques of Chapter 32, we can easily find duplicates on the basis of any one ID. But sometimes a person registers again after changing one or two IDs, while keeping another. For example, in a social sector scheme, each beneficiary is expected to register only once. A scheme audit may require the auditor to find duplicate beneficiaries across all the IDs together.

Let us understand this with Table 52.1.

PANs <- paste0(
  "PANNO", c("0000", "0000", "1111", "2222", "3333", "4444", "5555", "5555", "6666", "7777"),
  c("A", "A", "B", "C", "D", "E", "F", "F", "G", "H")
)

emails <- paste0(c("aaaa", "bbbb", "cccc", "dddd", "eeee", "ffff", "gggg", "hhhh", "iiii", "bbbb"), "@gmail.com")

  map_chr(~ rep(.x, 9) %>%
    paste0(collapse = "")))

dummy_data <- data.frame(
  ID = 1:10,
  Mobile = tele,
  Email = emails,
  PAN = PANs

Persons with IDs 6 and 10 share none of the three IDs, Mobile, Email and PAN. But look closely. ID-6 shares the mobile number with ID-1, who in turn shares the PAN with ID-2. ID-2 further shares both the email and the mobile number with ID-10. So ID-6 and ID-10 are linked, through a chain. Such chains are impossible to see in a table of thousands of rows. But they are obvious in a network, as in Figure 52.1. Note that we are not using names to find duplicates. Names are easily changed and often spelt differently.

id_long <- dummy_data |>

Notice the structure of this graph. It is bipartite. Persons are connected only to IDs, and IDs only to persons. Two persons are related if there is any path between them. In graph theory terms, all related persons fall in the same connected component. So all we have to do is find the components of this graph.

52.2.1 The algorithm

Here is the complete algorithm.

id_cols <- c("Mobile", "Email", "PAN")

dummy_data |>
  mutate(across(all_of(id_cols), as.character)) |>
  pivot_longer(cols = all_of(id_cols), names_to = "id_type",
               values_to = "value", values_drop_na = TRUE) |>
  mutate(id_node = paste(id_type, value, sep = ":")) |>
  select(ID, id_node) |>
  graph_from_data_frame(directed = FALSE) |>
  components() |>
  _$membership |>
  stack() |>
  set_names(c("UNIQUE_ID", "ID")) |>
  filter(!str_detect(ID, ":")) |>
  mutate(ID = as.integer(as.character(ID))) |>
  right_join(dummy_data, by = "ID")

We now have a UNIQUE_ID for each person, based on all three IDs together. Persons 1, 2, 5, 6 and 10 share one UNIQUE_ID, so they may be the same person, or a group acting together. Let us understand the algorithm step by step.

Step 1. All the ID columns must be of the same type. Real data often has a mix of character and numeric IDs, like a numeric mobile number and an alphanumeric PAN. Using across() inside mutate(), we convert all of them to character. Readers may refer to Section 1.4.1 for changing types, and Section 13.15 for changing many columns at once with across().

id_cols <- c("Mobile", "Email", "PAN")
dummy_data |>
  mutate(across(all_of(id_cols), as.character))

Step 2. Pivot all the ID columns into a longer format, so that each row links one person with one ID. Two things should be kept in mind. First, the data must have a column which identifies each record, here ID. If there is none, create one with row_number() before pivoting. Second, missing IDs must be removed while pivoting, using values_drop_na = TRUE. Otherwise, all persons with a missing PAN would be linked through the common value NA.

Step 3. Prefix each ID value with its type, like Mobile:9111111111. This is important. Without it, a value appearing in two different columns would become one vertex. For example, a record number "12" and a ward number "12" would wrongly link two records. Then we keep only the two columns we need, the record ID and the prefixed id_node. Up to this step, our data looks like this.

NoteNormalise the IDs first

In real data, the same ID is written in many ways, and each way would become a separate vertex. Before Step 2, standardise every ID column. Mobile numbers lose their +91 or 0 prefix with clean_mobile(), and email IDs are normalised with normalise_email(), both from Section 19.10. The second is especially important. Gmail ignores dots and +tags in the user name, so r.kumar@gmail.com and rkumar+scheme@gmail.com reach the same mailbox. Someone registering several times may use exactly this trick, and without normalising, the network would never connect those registrations.

Step 6. The membership includes the ID vertices too, like Mobile:9111111111. We keep only the person vertices, which have no : in their name. Their names are characters, so we convert them back to integers. Finally, we join the result back to the original data with right_join().

52.2.2 A bigger example, beneficiaries of a scheme

The small register showed the idea. Let us now try it on a more realistic register of 3,000 beneficiaries of an imaginary State scheme. The scheme pays ₹6,000 a year to each beneficiary, by direct benefit transfer into the bank account. Each beneficiary has a mobile number and a bank account. About 60% of them have also given a PAN. We have planted a few cases.

  • 60 pairs of beneficiaries share a mobile number. These are families, and genuine.
  • A ring of 7 registrations, each sharing one ID with the previous one, as if one person kept registering again, changing one ID at a time.
  • An agent’s mobile number, entered against 30 beneficiaries.
  • A placeholder mobile number, 9999999999, entered by data entry operators against 45 beneficiaries who did not give a number.

As usual, the code to create the data is folded.

Code to create the beneficiary register
set.seed(1234)
n <- 3000
rand_mobile <- function(k) paste0(sample(6:9, k, TRUE), sprintf("%09d", sample(0:999999999, k)))
rand_acct   <- function(k) sprintf("%011.0f", runif(k, 1e10, 9e10))
rand_pan    <- function(k) paste0(replicate(k, paste(sample(LETTERS, 5, TRUE), collapse = "")),
                                  sprintf("%04d", sample(0:9999, k, TRUE)), sample(LETTERS, k, TRUE))

ben <- tibble(ben_id  = sprintf("B%05d", 1:n),
              mobile  = rand_mobile(n),
              bank_ac = rand_acct(n),
              pan     = rand_pan(n))

# Genuine. 60 families share a mobile number
fam <- sample(1:n, 120)
ben$mobile[fam[61:120]] <- ben$mobile[fam[1:60]]

# Planted. A ring of 7 registrations, each sharing one ID with the previous one
ring <- c(101, 502, 903, 1304, 1705, 2106, 2507)

# PAN not given by about 40% of beneficiaries
ben$pan[sample(setdiff(1:n, ring), 0.4 * n)] <- NA

for (i in 2:length(ring)) {
  col <- c("mobile", "bank_ac", "pan")[(i %% 3) + 1]
  ben[[col]][ring[i]] <- ben[[col]][ring[i - 1]]
}

# Planted. An agent's mobile number on 30 beneficiaries
agent <- sample(setdiff(1:n, c(ring, fam)), 30)
ben$mobile[agent] <- "9876543210"

# Placeholder number entered when the mobile was not given
junk <- sample(setdiff(1:n, c(ring, fam, agent)), 45)
ben$mobile[junk] <- "9999999999"

Two values stand out at once. 9999999999 is obviously a placeholder, not a real number. If we keep it, it will link 45 unrelated beneficiaries into one false group. The other value, 9876543210, is linked with 30 beneficiaries. It looks genuine, and is exactly the kind of hub an auditor wants to find. It may be the number of an agent or a middleman, who registered and perhaps controls these beneficiaries. We drop the placeholder and keep the rest. In larger data, such junk values can be found systematically, before building any graph. A number made of one repeated digit is matched by the regex ^(\\d)\\1{9}$. IDs which fail their format or check digit can also be listed. Both are explained in Section 19.10 and Section 19.11.

ben_long <- ben_long |>
  filter(value != "9999999999")

Next, drop the leaf nodes. Most IDs belong to exactly one beneficiary. In the graph, such an ID is a leaf, a vertex with only one edge. A leaf can never link two beneficiaries, so it adds nothing to our analysis. It only makes the graph bigger. Let us compare the graph with and without them.

g_full <- graph_from_data_frame(select(ben_long, ben_id, id_node), directed = FALSE)

# Keep only IDs shared by at least two beneficiaries
ben_shared <- ben_long |>
  add_count(id_node) |>
  filter(n > 1)

g_ben <- graph_from_data_frame(select(ben_shared, ben_id, id_node), directed = FALSE)

tibble(graph    = c("All IDs", "Shared IDs only"),
       vertices = c(vcount(g_full), vcount(g_ben)),
       edges    = c(ecount(g_full), ecount(g_ben)))
# A tibble: 2 × 3
  graph           vertices edges
  <chr>              <dbl> <dbl>
1 All IDs            10660  7755

The graph has shrunk from 10,660 vertices to just 224, and the answer is not affected at all. Beneficiaries who share nothing with anyone have dropped out too, which is what we want. With real data of lakhs of records, this one step often makes the difference between a graph R can handle easily and one it cannot.

Now find the groups. Let us find the components, and count how many beneficiaries each one has.

ben_groups <- components(g_ben)$membership |>
  stack() |>
  set_names(c("group", "node")) |>
  filter(str_starts(node, "B")) |>
  count(group, name = "beneficiaries", sort = TRUE)

ben_groups |> count(beneficiaries, name = "number_of_groups")
  beneficiaries number_of_groups
1             2               60
2             7                1
3            30                1

There are 60 groups of two. These are mostly the families who share a mobile, which is normal. There is one group of 30, around the agent’s number. And there is one group of 7, the ring we planted. At ₹6,000 a year each, the ring draws ₹42,000 a year. The beneficiaries around the agent’s number draw ₹1.8 lakh a year. These amounts are at risk until the beneficiaries are verified. Let us draw the second largest group, in Figure 52.2.

# ben_groups is sorted by size. Take the second largest group.
ring_id <- ben_groups$group[2]
ring_nodes <- names(which(components(g_ben)$membership == ring_id))

ring_vis <- toVisNetworkData(ring_graph)

visNetwork(ring_vis$nodes, ring_vis$edges, width = "100%", height = "400px") |>
  visGroups(groupname = "Beneficiary", color = "steelblue", shape = "dot") |>
  visGroups(groupname = "mobile", color = "orange", shape = "square") |>
  visGroups(groupname = "bank_ac", color = "purple", shape = "triangle") |>
  visGroups(groupname = "pan", color = "tomato", shape = "diamond") |>
  visOptions(highlightNearest = TRUE) |>
  visLegend()

Each beneficiary in the chain shares only one ID with the next. No check on a single ID column would find more than a pair. Only the network shows the whole ring.

What next? The auditor would list the seven registrations with their names, addresses and dates of registration, and ask the scheme office to verify them. If they turn out to be one person, the payments to the extra registrations are recoverable. The agent’s number needs a field visit, to find out who the agent is and whether the 30 beneficiaries exist and receive their money.

TipAudit tip

The degree of an ID vertex, that is, the number of beneficiaries linked to it, is a quick way to find hubs. A mobile number or bank account linked with many beneficiaries deserves verification in the field. Who is the person behind it, and are the beneficiaries real?

52.3 Audit use case 2, bidders who bid together

Community detection, which we learnt in Chapter 51, classifies the vertices of a network into groups of closely linked vertices. In Section 51.10, we used it on links between firms from their registration papers. Often the auditor has no such papers, only the bids. Let us use the bids alone to find bid rigging. A cartel of firms agree among themselves who will win a tender. The others put in higher cover bids, to make the tender look competitive. Firms of a cartel therefore keep appearing in the same tenders. We looked for such firms with association rules in Chapter 45. Let us now look at the same problem as a network.

We create bids for 200 tenders of an imaginary Public Works Division over a few years. There are 40 firms, and 3 to 6 firms bid in each tender. We have planted a cartel of 5 firms, which bid together in every fourth tender.

Code to create the bids

    b <- union(sample(cartel, sample(3:5, 1)),
               sample(setdiff(firms, cartel), sample(0:2, 1)))

Tenders and firms form a bipartite graph. But we are interested in the relation between firms. So we project the bipartite graph onto the firms. 52.4 Audit use case 3, circular trading

In circular trading, a group of firms issue invoices to each other in a circle. A sells to B, B to C, C to D, and D back to A, often for nearly the same amount, within a few days. No real goods move. The purpose may be to show a false turnover to get bank loans, or to pass on input tax credit under GST fraudulently. In a network of invoices, where each firm is a vertex and each invoice a directed edge from seller to buyer, such trading shows up as a cycle.

Let us create the invoices of the financial year 2023-24 among the firms of a district. There are 15 manufacturers, 40 wholesalers and 150 retailers. Genuine goods flow one way, from manufacturers to wholesalers to retailers, so genuine trade has no cycles. We have planted two rings of circular trading. One ring of 4 firms went round twice, in September and November. Another ring of 3 retailers went round once, in January.

Pruning sources and sinks. There is another way to reach the same answer, which also makes big graphs much smaller. A firm which only sells and never buys (a source, with in-degree 0) cannot be part of a cycle. Neither can a firm which only buys and never sells (a sink, with out-degree 0). So we can delete them. But deleting them may turn other firms into sources or sinks, so we repeat until nothing more can be deleted. This is the directed version of dropping leaf nodes.

  if (length(drop) == 0) break
  pruned <- delete_vertices(pruned, drop)

52.5 Audit use case 4, vendors linked with employees

A vendor which is secretly owned or controlled by an employee of the organisation is a classic conflict of interest. The employee may push its bills, approve inflated rates, or pass on inside information. Such a link usually leaves traces in the data. The employee and the vendor may share a bank account, a mobile number or an address. Sometimes the link is indirect, through a relative or a third firm.

This is the same problem as use case 1, but across two masters. Let us create an employee master of 150 employees and a vendor master of 80 vendors, each with a bank account, a mobile number and an address. We have planted three links.

  • Vendor V051 has the same address as employee E033.

52.6 Tips for working with big networks

Real audit data has lakhs of records. A network built carelessly from such data can be too big to analyse, or full of false links. Here are some tips which help.

1. Drop the leaf nodes. Most IDs belong to only one record. In the graph, these are leaves, vertices with only one edge, and they can never link two records. Dropping them shrinks the graph enormously without changing the answer. We can drop them either before building the graph, or after.

# Before building the graph, with dplyr
edges_shared <- edges_long |>
  add_count(id_node) |>
  filter(n > 1)

# After building the graph, with igraph.
# Delete ID vertices with one edge, then records left with no edge
g <- delete_vertices(g, V(g)[degree(g) == 1 & str_detect(name, ":")])
g <- delete_vertices(g, V(g)[degree(g) == 0])

In a directed graph where we look for cycles, we drop sources and sinks repeatedly, as we did in use case 3. For an undirected graph where we look for tightly knit groups, the same idea is the k-core. The 2-core is what remains after repeatedly removing all vertices with fewer than 2 edges. coreness() gives the core number of each vertex, so induced_subgraph(g, V(g)[coreness(g) >= 2]) keeps the 2-core.

2. Prefix every ID with its type. Write mobile:9876543210, not 9876543210. Otherwise two different kinds of ID which happen to have the same value become one vertex, and create false links.

3. Look at the most connected IDs first, and remove junk values. Some values are only placeholders, like 9999999999, 0000000000, NA, test@gmail.com, XXXXX0000X, or the address of the office itself. Such a value links hundreds of unrelated records into one giant group. Always run count(id_node, sort = TRUE) before building the graph. Remove the junk values, and keep the genuine hubs aside for separate examination.

4. Clean before you connect. 9876543210, +91 98765 43210 and 09876543210 are the same mobile number. r.kumar@gmail.com and rkumar+bids@gmail.com are the same Gmail box. Standardise IDs before building the graph, with the functions of Chapter 18 and Section 19.10, like clean_mobile() and normalise_email(). Otherwise real links are missed.

5. Validate before you connect. An ID in the wrong format, or with a wrong check digit, cannot be a genuine shared ID. A mistyped Aadhaar or GSTIN may by chance equal someone else’s, and create a false link. Run the format and check digit tests of Section 19.10 and Section 19.11 first. Keep the invalid IDs out of the graph, and report them separately as data quality findings.

6. Work with components, not with the whole graph. Use components() to split the graph, and then study the components of interest one at a time with induced_subgraph(). Sort them by size. Groups of 2 are usually families or genuine. Very large groups usually mean a junk value is still present.

7. Beware of bipartite projection with hubs. When we project a bipartite graph, an ID shared by \(d\) records creates \(d(d-1)/2\) edges. One junk value shared by 10,000 records would create about five crore edges. Remove junk values and big hubs before projecting.

8. Draw only what matters, and draw it fast. Plot a component or an ego network, not the whole graph. For visNetwork, use visIgraphLayout(), so that the layout is calculated once in R and the browser does not have to run its slow physics simulation. Keep labels short, and put details in the title (tooltip).

9. Keep the record keys and amounts. Keep the original record IDs, invoice numbers, amounts and dates as attributes of vertices and edges. Every finding has to be traced back to the documents, and quantified in rupees.

TipShare the network

visSave(network, file = "ring.html") saves an interactive network as a single HTML file. It can be emailed to the audit team or attached to the working papers, and opened in any browser without R.

52.7 A suggested workflow

  1. Decide the vertices and edges. What are the entities (persons, firms, accounts), and what links them (shared IDs, bids, invoices)? Is the graph directed?
  2. Prepare the data. Clean, standardise and validate the IDs (Section 19.10), prefix them with their type, and pivot to one row per link.
  3. Look at the most connected IDs. Remove junk values. Note the genuine hubs.
  4. Reduce the graph. Drop leaves, sources and sinks, or take the k-core, depending on the question.
  5. Find the structure. Components for related entities, communities for groups, cycles for circular flows, shortest paths to explain a link, centrality for key players.
  6. Visualise the parts of interest with visNetwork, and share them.
  7. Go back to the records. Verify every lead with documents, and quantify it.
ImportantRemember

A link in a network shows that two records share something. It does not show why. Family members share mobiles, neighbours share addresses, and specialised firms meet in the same tenders. A network gives leads, not findings. Every lead must be verified with documents, and where needed, in the field.
