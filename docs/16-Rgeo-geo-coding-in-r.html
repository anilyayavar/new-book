54  Geocoding

Most records give location as an address, not as coordinates. A vendor’s address, a beneficiary’s village, a hospital’s location. To put such records on a map, or to measure distances between them, we must first convert the address into latitude and longitude. This is called geocoding.

The reverse, converting latitude and longitude into an address, is called reverse geocoding. We will learn it in the next chapter.

54.1 Where can geocoding help an auditor?

  • Checking claimed distances. Travel allowance, transport charges and freight claims depend on distance. Geocoding the places lets us compare the claimed distance with the actual one.
  • Shared locations. Two “different” vendors, or many beneficiaries, at the same address can point to fake entities or duplicate registration. This complements the duplicate tests of Chapter 32.
  • Distance between supplier and site. A supplier located far away from the delivery site may be a front for someone else, or may be charging for transport that never happened.
  • Mapping records which only have addresses, so that the techniques of Chapter 53 can be applied.

54.2 How geocoding works

A geocoding service keeps a large database of places and addresses with their coordinates. We send it an address as text. It searches for the best match, and returns the coordinates, along with details like the full address it matched.

Several services are available.

  • OpenStreetMap Nominatim. Free and open, based on the OpenStreetMap community map. It is the default in R’s tidygeocoder package. Its usage policy allows only light use, about one request per second, and asks users to credit OpenStreetMap.
  • Commercial services, such as those offered by Google, ArcGIS and several Indian map providers. They often give better results for Indian addresses, but need an account and an API key, and usually charge beyond a free limit.
WarningNever send personal data to a public service

Geocoding sends your addresses to someone else’s server. Do not send addresses of beneficiaries, patients, employees or taxpayers to public services. Use only services approved by your organisation for such data. In this chapter, we geocode only public places, such as monuments and well-known markets.

54.3 Prerequisites

We will use tidygeocoder for geocoding, and sf for distances.

library(tidyverse)
library(tidygeocoder)
library(sf)

54.4 Geocoding a few places

The function geocode() from tidygeocoder works on a data frame. We tell it which column holds the address, and which service (method) to use. Let us geocode a few well-known places.

places <- tibble(place = c("Taj Mahal, Agra",
                           "Hawa Mahal, Jaipur",
                           "Charminar, Hyderabad",
                           "Victoria Memorial, Kolkata",
                           "Gateway of India, Mumbai",
                           "Xyzabc Nagar, Nowhere"))

places_geo <- places |>
  geocode(address = place, method = "osm")

TipGeocode once, save the result

Geocoding is slow, and free services limit how much you can use them. Do not geocode the same addresses again and again. Geocode once, save the result with write_csv(), and read the saved file in later work.

54.4.1 More details about each match

With full_results = TRUE, the service returns everything it knows about the match. This is useful to judge the quality of each match.

places_geo_full <- places |>
  slice(1:3) |>
  geocode(address = place, method = "osm", full_results = TRUE)

places_geo_full |>
  select(place, lat, long, display_name, class, type)
# A tibble: 3 × 6
  place                  lat  long display_name                      class type 
  <chr>                <dbl> <dbl> <chr>                             <chr> <chr>
1 Taj Mahal, Agra       27.2  78.0 Taj Mahal, Taj East Gate Road, T… hist… tomb

The display_name column shows the full address that the service actually matched. The class and type columns tell what kind of place it is. Reading these is the best way to catch wrong matches.

WarningBeware of approximate matches

When a service cannot find the exact address, it often returns the centre of the town, district or pin code instead, without any warning. In Indian addresses, which are often written in very different ways, this is common. So two vendors may appear to be at “the same location” only because both were matched to the centre of the same town. Always look at what was matched, before drawing conclusions.

54.5 From coordinates to map points

Latitude and longitude are in the WGS 84 coordinate system, whose code is EPSG:4326. We met coordinate systems in Chapter 53. To turn the geocoded table into map points, we use st_as_sf(). Note that the longitude comes first, because it is the x-coordinate.

places_sf <- places_geo |>
  filter(!is.na(lat)) |>
  st_as_sf(coords = c("long", "lat"), crs = 4326)

54.5.1 Measuring distances

dimnames(dist_km) <- list(places_sf$place, places_sf$place)

These are straight-line distances, as a bird would fly. Roads and railway lines are always longer. This simple fact is the basis of our first audit check.

54.6 Audit use case 1, checking claimed travel distances

Suppose a department pays travel allowance partly on the basis of the distance claimed by the employee. Let us check a few claims. The table below is made up. The places are well-known towns.

ta_claims <- tribble(
  ~claim_no, ~from,               ~to,                   ~claimed_km,
  "TA-01",   "Lucknow",           "Varanasi",            320,
  "TA-02",   "Bhopal",            "Indore",              195,
  "TA-03",   "Patna",             "Gaya",                115,
  "TA-04",   "Jaipur",            "Ajmer",               60,
  "TA-05",   "Dehradun",          "Haridwar",            160,
  "TA-06",   "Bhubaneswar",       "Puri",                65
)

We need the coordinates of each town. Since a town appears in more than one claim, we geocode each town only once.

towns <- tibble(town = unique(c(ta_claims$from, ta_claims$to))) |>
  mutate(address = paste0(town, ", India")) |>
  geocode(address = address, method = "osm")

We added “, India” to each name, so that the service does not pick a town of the same name in another country. Now we join the coordinates to both ends of each claim, and measure the straight-line distance.

from_pts <- ta_claims |>
  left_join(towns, by = c("from" = "town")) |>
  st_as_sf(coords = c("long", "lat"), crs = 4326)

to_pts <- ta_claims |>
  left_join(towns, by = c("to" = "town")) |>
  st_as_sf(coords = c("long", "lat"), crs = 4326)

ta_checked <- ta_claims |>
  mutate(straight_km = round(as.numeric(st_distance(from_pts, to_pts, by_element = TRUE)) / 1000),
         ratio = round(claimed_km / straight_km, 2))

ta_checked

How do we read the ratio? Road distance in India is usually around 1.2 to 1.5 times the straight-line distance. So a ratio in that range is normal.

  • A ratio below 1 is impossible. No road is shorter than a straight line. Such a claim is certainly wrong. Here, that means the claim from Jaipur to Ajmer.
  • A ratio far above 1.5 suggests an inflated claim. Here, the claim from Dehradun to Haridwar is more than three times the straight-line distance.
ta_checked |>
  filter(ratio < 1 | ratio > 1.8)
# A tibble: 2 × 6
  claim_no from     to       claimed_km straight_km ratio
  <chr>    <chr>    <chr>         <dbl>       <dbl> <dbl>
1 TA-04    Jaipur   Ajmer            60         127  0.47
2 TA-05    Dehradun Haridwar        160          44  3.64
NoteStraight-line or road distance?

The straight-line distance is a quick filter, not the final answer. For the flagged claims, check the actual road or rail distance from official tables, or from a routing service. Some routes are genuinely long because of hills, rivers or the lack of a direct road.

54.7 Audit use case 2, different vendors, same place

In Chapter 32, we found look-alike vendor names. Another sign of fake or related vendors is that their addresses point to the same place, even though they are written differently. Let us look at a few vendors of a department. The addresses are of well-known commercial areas, and the vendors are made up.

vendors <- tribble(

Two vendors share a location. But what happened to the third Nehru Place vendor? Let us see what the service actually matched for each of the three addresses.

vendors |>
  filter(str_detect(address, "Nehru Place")) |>
  geocode(address = address, method = "osm", full_results = TRUE) |>
  select(vendor, address, display_name)

“Nehru Place, New Delhi” has been matched to Motilal Nehru Place, a road in central Delhi, several kilometres away from the Nehru Place market. A small difference in how the address was written led to a completely different place. This is exactly the problem of approximate matches that we warned about earlier. An auditor who relied on the coordinates alone would have missed that all three vendors are in the same market.

So the analysis finds two vendors at one spot, and a careful reading of the matched addresses adds the third. Three “different” vendors are located in the same market. This is not wrong by itself. A market like Nehru Place has hundreds of shops. But if these three vendors also bid in the same tenders, as in Chapter 45, or share a phone number or bank account, the case for a closer look becomes strong.

TipAudit tip

Rounding to three decimal places groups points within about 100 metres. Rounding to four places, about 10 metres, is stricter. Choose according to the quality of your addresses. With precise addresses, use four places. With addresses that only give a locality, three or even two places may be better.

54.8 Audit use case 3, excess lead charges in works

In road and building works, contractors are paid for carrying materials like stone aggregate from a quarry to the work site. This carriage charge is called lead, and it is paid per cubic metre per kilometre. So the longer the claimed lead, the bigger the payment. Two common irregularities are,

  • claiming carriage from a distant quarry, when an approved quarry is much nearer, and
  • claiming a lead much longer than the actual distance to the quarry named.

Excess payment on lead is a frequent finding in audits of works. Let us check six works in Rajasthan. The work sites are real towns. The quarries, quantities and claims are made up, and the carriage rate is imaginary.

works <- tribble(
  ~work_id, ~site,       ~quantity_cum, ~claimed_quarry,  ~claimed_lead_km,
  "W-01",   "Churu",      12000,        "Bikaner",         175,
  "W-02",   "Sikar",      15000,        "Kotputli",        150,
  "W-03",   "Nagaur",      9000,        "Jodhpur",         135,
  "W-04",   "Jhunjhunu",  18000,        "Jodhpur",         410,
  "W-05",   "Tonk",       10000,        "Sawai Madhopur",   85,
  "W-06",   "Bhilwara",   14000,        "Kishangarh",      290
)

approved_quarries <- c("Kishangarh", "Bikaner", "Jodhpur", "Kotputli", "Sawai Madhopur")
rate_per_cum_km <- 4.5   # rupees, imaginary

We geocode each town once, sites and quarries together.

rj_towns <- tibble(town = unique(c(works$site, approved_quarries))) |>
  mutate(address = paste0(town, ", Rajasthan, India")) |>
  geocode(address = address, method = "osm")

rj_sf <- rj_towns |> st_as_sf(coords = c("long", "lat"), crs = 4326)
quarry_sf <- rj_sf |> filter(town %in% approved_quarries)

For each work, we need two distances. First, the straight-line distance to the quarry it claims. Second, the straight-line distance to the nearest approved quarry. st_nearest_feature() gives, for each point, the row number of the nearest feature in another layer.

site_sf <- works |>
  left_join(rj_towns, by = c("site" = "town")) |>
  st_as_sf(coords = c("long", "lat"), crs = 4326)

claimed_sf <- quarry_sf[match(works$claimed_quarry, quarry_sf$town), ]
nearest_sf <- quarry_sf[st_nearest_feature(site_sf, quarry_sf), ]

lead_check <- works |>
  mutate(km_to_claimed  = round(as.numeric(st_distance(site_sf, claimed_sf, by_element = TRUE)) / 1000),
         nearest_quarry = nearest_sf$town,
         km_to_nearest  = round(as.numeric(st_distance(site_sf, nearest_sf, by_element = TRUE)) / 1000),
         lead_ratio     = round(claimed_lead_km / km_to_claimed, 2))

lead_check |>
  select(work_id, site, claimed_quarry, claimed_lead_km, km_to_claimed, lead_ratio,
         nearest_quarry, km_to_nearest) |>
  print(width = Inf)

Two works stand out.

  • W-04 at Jhunjhunu claims stone from Jodhpur, although the approved quarry at Kotputli is much nearer. Its lead ratio is normal. The distance claimed is genuine, but the quarry choice is not.
  • W-06 at Bhilwara names the nearest quarry, Kishangarh, but claims a lead of more than twice the straight-line distance.

To estimate the excess payment, we take a reasonable lead as 1.3 times the straight-line distance to the nearest approved quarry, as discussed in use case 1. Any lead claimed beyond this is excess.

lead_excess <- lead_check |>
  mutate(reasonable_lead_km = round(1.3 * km_to_nearest),
         excess_km          = pmax(claimed_lead_km - reasonable_lead_km, 0),
         excess_rupees      = excess_km * quantity_cum * rate_per_cum_km) |>
  filter(excess_km > 0.2 * reasonable_lead_km) |>
  select(work_id, site, claimed_lead_km, reasonable_lead_km, excess_km, quantity_cum, excess_rupees)

lead_excess |> print(width = Inf)

54.8.1 An interactive map

For presenting such findings, and for exploring them, an interactive map helps. The package leaflet draws maps which can be zoomed and clicked, with OpenStreetMap as the background. Unlike our imaginary state in Chapter 53, these are real places with latitude and longitude, so leaflet can place them on a real map (Figure 54.1). Click a line to see the claim.

library(leaflet)

# One straight line from each work site to its claimed quarry
route_lines <- map2(st_geometry(site_sf), st_geometry(claimed_sf),
                    \(a, b) st_linestring(rbind(st_coordinates(a), st_coordinates(b)))) |>
  st_sfc(crs = 4326) |>
  st_sf(geometry = _) |>
  mutate(work_id = works$work_id,
         flagged = work_id %in% lead_excess$work_id,
         popup   = paste0(work_id, ": ", works$site, " to ", works$claimed_quarry,
                          "<br>Claimed lead ", works$claimed_lead_km, " km"))

leaflet(width = "100%", height = 450) |>
  addTiles() |>
  addPolylines(data = route_lines, color = ~if_else(flagged, "red", "grey"),
               weight = 3, popup = ~popup) |>
  addCircleMarkers(data = site_sf, radius = 5, color = "steelblue", label = ~site) |>
  addCircleMarkers(data = quarry_sf, radius = 6, color = "darkgreen", label = ~town)
TipAudit tip

When a work claims material from a distant quarry, ask why the nearer approved quarry was not used. Sometimes there is a good reason, like the quality of stone or the nearer quarry being closed. That reason must be on record, with the approval of the competent authority, before the work was done. Also compare the claimed lead with the lead chart approved for the district, if one exists.

54.9 A suggested workflow

  1. Use an approved service. Never send personal addresses to a public geocoder.
  2. Clean the addresses first. Add the state and “India”, remove extra spaces, and expand common short forms.
  3. Geocode each unique address once, and save the results.
  4. Check the failures (NA coordinates) and the quality of matches, using full_results = TRUE.
  5. Turn the results into points with st_as_sf(coords = c("long", "lat"), crs = 4326).
  6. Measure distances with st_distance(), and compare with claims.
  7. Look for shared locations, by rounding coordinates.
  8. Verify each flagged case with records, and with official distance tables or site visits.
ImportantRemember

Geocoding gives the location of the address as written, not necessarily the location of the thing. A wrong or vague address gives a wrong or vague location. Treat geocoded locations as approximate, and always look at the matched address before drawing a conclusion.
